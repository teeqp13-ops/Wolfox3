# بنية متجر ولفوكس

## التدفق الأساسي

1. تعرض الواجهة المنتجات الفعالة من SQLite، ولا تثق بالسعر القادم من المتصفح.
2. ينشئ `/api/orders.php` طلباً بحالة `pending` بعد التحقق من Telegram init data عند توفرها.
3. ترسل بوابة الدفع webhook إلى `/payment/callback.php`.
4. يحفظ المتجر حدث الدفع بمفتاح فريد، لذلك إعادة إرسال webhook لا تكرر العملية.
5. عند حالة `paid` يحجز النظام أول كود متاح للمنتج داخل معاملة SQLite فورية.
6. يرسل `DeliveryService` الكود عبر Telegram و/أو NeraChat WhatsApp، ويسجل كل محاولة.

## حدود الإصدار الأول

- محول EdfaPay يحتوي التحقق والتطبيع العام، لكن حقول إنشاء جلسة الدفع يجب مطابقتها مع عقد حساب التاجر قبل الإنتاج.
- لوحة الإدارة للقراءة والمتابعة في هذا الإصدار؛ إدارة المنتجات والمخزون تتم من سكربتات CLI.
- لا توجد أسرار داخل المستودع. جميع المفاتيح في `.env` فقط.

## الحماية

- توقيع Telegram Web App يتم التحقق منه حسب HMAC ومدة `auth_date`.
- السعر والعملة يؤخذان من قاعدة البيانات.
- أحداث الدفع idempotent بفضل `payment_events.event_key` الفريد.
- حجز الأكواد مشروط بالحالة `available` داخل معاملة كتابة SQLite لتجنب التسليم المكرر.
- لوحة الإدارة محمية بـ HTTP Basic وكلمة مرور مخزنة كـ password hash.
- ردود الأخطاء العامة لا تكشف مفاتيح أو تفاصيل قاعدة البيانات.
